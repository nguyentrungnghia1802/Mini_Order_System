# Database

Last reviewed: 2026-08-02.

## 1. Source of truth

Each service owns its Entity Framework Core migration history.

Expected migration locations:

```text
src/Services/ProductService/Persistence/Migrations/
src/Services/OrderService/Persistence/Migrations/
src/Services/NotificationService/Persistence/Migrations/
```

Rules:

1. EF Core migrations and runtime model configuration are the executable schema source of truth.
2. This document describes intent and must be updated with schema changes.
3. Migrations run per service/database.
4. Normal application startup must not silently apply production migrations.
5. Local development may use an explicit migration command or controlled migration container.
6. No migration may create tables in another service's database.
7. Already applied migration names are immutable.

## 2. Local database topology

For local simplicity, one PostgreSQL server hosts separate logical databases:

| Database | Owner service | Suggested user |
| --- | --- | --- |
| `microshop_product` | Product Service | `product_app` |
| `microshop_order` | Order Service | `order_app` |
| `microshop_notification` | Notification Service | `notification_app` |

The users should have access only to their database. A bootstrap/init script may create databases and roles; it must not create business tables. Business tables come from service migrations.

## 3. Cross-service relationship rule

There are no database foreign keys across services.

For example:

- `order_items.product_id` is a UUID snapshot reference, not an FK to Product DB;
- `inventory_reservations.order_id` is a UUID idempotency/reference value, not an FK to Order DB;
- `notifications.order_id` is event data, not an FK to Order DB.

Referential meaning is maintained through service contracts and immutable snapshots.

## 4. Product database logical model

```text
products
  1
  |
  *
inventory_reservation_items
  *
  |
  1
inventory_reservations
```

Optional audit extension:

```text
products 1 --- * product_stock_movements
```

| Column | Type | Rules |
| --- | --- | --- |
| `id` | uuid | PK, generated by application or database |
| `name` | varchar(200) | required |
| `description` | varchar(2000) | nullable |
| `unit_price` | numeric(18,2) | nonnegative |
| `currency` | varchar(3) | `VND` baseline |
| `available_stock` | integer | nonnegative |
| `is_active` | boolean | required |
| `created_at_utc` | timestamptz | required |
| `updated_at_utc` | timestamptz | required |
| `version` or PostgreSQL `xmin` | concurrency token | required behavior |

Indexes:

- active catalog ordering index on `(is_active, name, id)`;
- optional case-insensitive search index later.

### `inventory_reservations`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | uuid | PK |
| `order_id` | uuid | unique |
| `request_hash` | varchar | canonical item-set hash |
| `status` | varchar | `reserved`, `released` |
| `created_at_utc` | timestamptz | required |
| `released_at_utc` | timestamptz | nullable |

Constraints:

- unique `order_id`;
- status check;
- release timestamp consistent with status.

### `inventory_reservation_items`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | uuid | PK |
| `reservation_id` | uuid | FK within Product DB |
| `product_id` | uuid | FK to `products` |
| `product_name` | varchar(200) | reservation snapshot |
| `unit_price` | numeric(18,2) | snapshot |
| `quantity` | integer | positive |
| `subtotal` | numeric(18,2) | nonnegative |

Constraints:

- unique `(reservation_id, product_id)`;
- positive quantity;
- subtotal uses fixed decimal semantics.

### Optional `product_stock_movements`

Useful in a hardening phase:

| Column | Purpose |
| --- | --- |
| `id` | movement ID |
| `product_id` | local FK |
| `type` | `initial`, `adjustment`, `reservation`, `release` |
| `quantity_delta` | signed integer |
| `order_id` | nullable external reference |

The baseline can operate without this table because reservations already explain order-related stock changes.

## 7. Critical constraints

1. Money columns use `numeric`, mapped to C# `decimal`.
2. All timestamps use `timestamptz` and UTC.
3. Stock and quantities use integers.
4. Product stock has a database check `available_stock >= 0`.
5. Reservation order ID is unique.
6. Reservation items are unique per product.
7. Order items are unique per product.
8. Notification source message ID is unique.
9. State values use check constraints or PostgreSQL enums only when migration complexity is accepted.
10. String status plus check constraints is preferred for this small project because it is easy to evolve and inspect.

## 8. Transaction boundaries

### Product creation/update

One Product DB transaction, normally one `SaveChanges`.

### Bulk inventory reservation

One Product DB transaction:

1. check existing reservation by order ID;
2. canonical mismatch check;
3. lock all products in stable ID order to reduce deadlock risk;
4. validate all rows;
5. decrement stock;
6. insert reservation and item snapshots;
7. commit.

No remote call occurs while the Product DB transaction is open.

### Inventory release

One Product DB transaction:

1. lock reservation and items;
2. return idempotent result if already released;
3. restore stock;
4. mark released;
5. commit.

### Initial order persistence

One Order DB transaction:

- insert order `pending_inventory`;
- insert creation state history;
- commit before remote reservation call.

### Order confirmation

One Order DB transaction:

- verify current state;
- insert order items;
- set total and `confirmed`;
- insert state history;
- insert outbox event when outbox phase is enabled;
- commit.

### Notification consume

One Notification DB transaction:

- insert/check consumed message;
- insert notification when new;
- commit.

## 9. Concurrency strategy

### Product stock

Preferred approaches:

- explicit `SELECT ... FOR UPDATE` through Npgsql/raw SQL for requested rows; or
- atomic conditional update with row-count validation.

The selected implementation must be tested with real PostgreSQL concurrency. EF Core InMemory is not a valid concurrency test.

Rows are locked in sorted product-ID order to reduce deadlocks for overlapping multi-item orders.

### Order transitions

Use a concurrency token and status guard:

```text
UPDATE orders
SET status = ...
WHERE id = ... AND status = expected_status AND version = expected_version
```

A zero-row update returns `409 ORDER_STATE_CONFLICT`.

## 10. Idempotency persistence

| Operation | Storage |
| --- | --- |
| Reserve stock | unique `inventory_reservations.order_id` plus `request_hash` |
| Release stock | reservation status |
| Consume event | `consumed_messages` PK/unique |
| Publish event | `outbox_messages.id` and publish state |
| Optional public order retry | separate idempotency table or unique client key, deferred |

Idempotency state must be durable; in-memory dictionaries are insufficient.

## 11. Migration workflow

For each service:

```bash
dotnet ef migrations add <Name> \
  --project <ServiceProject> \
  --startup-project <ServiceProject>

dotnet ef database update \
  --project <ServiceProject> \
  --startup-project <ServiceProject>
```

Repository scripts should wrap the exact paths.

Rules:

1. model change and migration are one commit;
2. migrations are reviewed for destructive operations;
3. startup validates database connectivity but does not conceal migration failure;
4. CI creates empty databases and applies all migrations;
5. rollback uses application/database backup strategy, not casual migration removal;
6. production deploy applies migrations before new service instances receive traffic;
7. data migrations are explicit and restart-safe.

## 12. Seed and fixture profiles

### Minimal development seed

Product DB only:

- 3–5 active products;
- one inactive product;
- varied stock including zero.

No orders or notifications are required in minimal seed.

### Integration fixtures

Tests create their own data with unique IDs. They must not depend on the developer seed.

### Demo fixture

Optional deterministic script creates:

- products;
- one confirmed order and reservation;
- one rejected order;
- one notification.

Demo fixture is blocked in production configuration.

## 13. Deletion and retention

Baseline policy:

- products are deactivated, not hard-deleted;
- orders are retained;
- reservations are retained;
- notifications are retained for the life of the demo database;
- local reset may destroy all volumes.

A production extension must define personal-data retention for customer name/email.

## 14. Sensitive data

Even without authentication, the database contains demo personal data:

- customer name;
- customer email.

Rules:

- use fictional data in seeds and screenshots;
- do not log full request bodies;
- mask email when high-detail logs are unnecessary;
- backups must be protected;
- public deployment must add authentication before accepting real personal data.

## 15. Backup boundaries

Each database is backed up independently or from one PostgreSQL server dump that preserves database separation.

A complete logical recovery also requires:

- RabbitMQ definitions/configuration;
- application configuration;
- matching service versions.

Pending broker messages are not replaced by database backup. In outbox mode, unpublished order events can be regenerated from Order DB outbox rows.
